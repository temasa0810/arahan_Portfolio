MB_BYPASS

인가된 모바일 보안 평가를 위한 멀티에이전트 리버싱 자동화 CLI. Java(jadx) + Native(.so, Ghidra) 탐지 로직을 병렬 분석하고, Frida 후킹으로 런타임 검증하며, 실측과 추정을 구분한 평가 리포트를 생성한다.

비공개·비배포 프로젝트. 본 도구는 상용·금융 앱에 대한 동작하는 우회 코드를 포함하므로 소스를 배포하지 않는다. 이 페이지는 도구의 설계·인터페이스·방법론만 공개한다. 코드 열람·라이브 데모는 인가된 평가 맥락 또는 면접 시 제공한다. → 윤리·인가 고지

무엇을 하는가

모바일 보안 솔루션 분석의 전체 워크플로를 하나의 CLI로 구동한다.

① recon      보호 표면 매핑      네이티브 .so + Java를 시그니처 DB와 대조, 실행 중 로드 .so 열거
② analyze    탐지 로직 분석      Java(jadx) ∥ Native(Ghidra) 병렬, FindingSet JSON 산출
③ hook       동적 검증·우회      findings → Frida 후킹 생성 → attach → 실발동 확인
④ report     평가 리포트         결과 집계, 실측/추정 구분 표기 (md + 자체완결 html)

핵심 설계 원칙은 "뚫었다/못 뚫었다"가 아니라 결론의 정확도다. 정적 코드에 경로가 있다는 것과 런타임에 그 경로가 실제로 쓰인다는 것을 구분하며, 증적 없는 판정은 "미규명"으로 남긴다. 이 규율은 설명이 아니라 데이터 모델에 강제되어 있다(아래 참조).

아키텍처

5개 전용 에이전트(java-detection-analyst, native-detection-analyst, frida-hook-engineer, bypass-report-writer, adversarial-reviewer)가 역할을 분담하며, 반대자 에이전트가 모든 부정 결론을 게이트한다.

실제 인터페이스

$ mb-bypass --help
Authorized Android security-solution bypass analysis toolkit.

  recon      보호 표면을 먼저 매핑 (native .so + Java vs 시그니처 DB)
  analyze    java | native  탐지 로직 정적/네이티브 분석
  hook       gen | run      Frida 후킹 생성 및 실행
  report     결과 집계 → 리포트 (--html)
  results    sync | path    결과 마스터 영속화 헬퍼

$ mb-bypass recon   --package <pkg> --live
$ mb-bypass analyze java   target/<pkg>/jadx_out      --engine mcp
$ mb-bypass analyze native target/<pkg>/lib/libX.so   --engine mcp
$ mb-bypass hook gen  results/<pkg>/native_findings.json
$ mb-bypass hook run  results/<pkg>/generated/hook.js -t <pkg> --spawn
$ mb-bypass report   --html

결과는 타깃별로 results/<package>/에 격리되어, 여러 앱을 동시에 다뤄도 findings가 섞이지 않는다.

산출물 — FindingSet (판단 규율이 박힌 데이터 모델)

각 분석 단계는 구조화된 FindingSet JSON을 주고받는다. 아래는 스키마 예시(값은 비실명).

{
  "source": "native:libexample.so",
  "findings": [
    {
      "id": "nat-001",
      "layer": "native",
      "location": "libexample.so!0xXXXXX (JNI_OnLoad)",
      "category": "frida-detection",
      "evidence": "thread-name scan over /proc/self/task/*/comm",
      "confidence": 0.9,
      "status": "bypassed",
      "hook_target": { "module": "libexample.so", "symbol": "<resolved>" }
    }
  ]
}

주목할 것은 status 필드의 상태값이다 — 이것이 방법론을 코드로 강제한다.

status의미
untested발견했으나 후킹 미실행
confirmed정적/동적 분석으로 탐지 로직 확인
hookedFrida 후킹이 실제 발동 → 탐지 로직 확정
not_hooked후킹 걸었으나 발동 안 함
not_observed정적으론 확인됐으나 관측 창에서 런타임 미발동 (static ≠ runtime)
bypassed후킹으로 탐지 무력화 성공

not_observed의 존재가 핵심이다. "코드에 탐지 로직이 있다"와 "그 로직이 실제로 돈다"를 데이터 모델 레벨에서 분리하여, 정적 경로의 존재를 런타임 사실로 오인하지 못하게 한다.

기술 스택

  • 언어/런타임 — Python 3.10+ (CLI 오케스트레이션), JavaScript (Frida 에이전트)
  • 동적 계측 — Frida 17.x (florida 원격 서버 1순위 / ZygiskFrida 로드타임 gadget 2순위)
  • 정적 분석 — jadx (Java), Ghidra (Native .so) — 각각 MCP API로 분석 에이전트가 직접 구동
  • 오케스트레이션 — 5-에이전트 하이브리드 파이프라인 (병렬 분석 / 리더 종합 / 반대자 게이트 / 순차 후킹·리포트)
  • 산출물 — FindingSet JSON으로 단계 간 결합, 마크다운 + 자체완결 HTML 리포트

규모

  • 20+ 안드로이드 실앱 인가 분석 (상용 게임 · 금융 · RASP 적용 앱) + 공인 CTF 다수
  • 5 전용 분석 에이전트 + 1 상설 반대자
  • 다수 타깃 비종속 재사용 기법 + 판단 교훈을 구조화된 지식 베이스로 누적
  • 상용 네이티브 안티치트 계열·상용 RASP(금융권)·Unity IL2CPP 난독화 등 고난도 보호 환경 포함

상태

  • 비공개 · 인가 전용 · 비배포. 소스·바이너리를 배포하지 않는다.
  • 핵심 파이프라인(recon→analyze→hook→report) 동작, 다수 실 타깃에 적용 완료.
  • 일부 고난도 타깃은 분석 진행 중이며, 미규명 항목을 정직하게 표기한다.
