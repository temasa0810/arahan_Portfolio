자가삭제 보안모듈 복구 — unlink 후킹

실행 중 자신을 삭제하는 보안모듈을 메모리에서 보존해 정적 분석하는 과정 · 인가 분석 · 비실명
방법론 기둥 — 자가삭제 모듈 복구(§5.1). 탐지 후 자신을 unlink하는 보안 모듈을 프로세스 메모리에서 식별한 뒤 unlink 후킹으로 삭제를 차단해 보존하고 정적 분석으로 복원한다. 일반화된 재사용 기법으로, 특정 제품에 종속되지 않는다. → 방법론 보기
비실명 고지. 대상 앱·보안 벤더·모듈명·함수명·오프셋 등 식별 정보는 제거하였다. 본 글은 분석 방법을 설명하며, 특정 제품의 동작하는 우회 코드·오프셋은 포함하지 않는다. 모든 분석은 인가된 환경에서 수행되었다.

대상 개요 (비실명)

항목상태
개발 엔진Unity (IL2CPP)
보안 솔루션상용 모바일 게임 보안 솔루션 (벤더 비실명)
루팅 탐지없음
후킹 & 디버깅 탐지있음
보안 모듈(.so) 난독화없음 — 단, 실행 후 자가삭제로 분석 방해

핵심 보안 모듈은 게임 실행 시 복호화·로딩되어 탐지를 수행한 뒤 스스로 모듈 파일을 삭제한다. 이 "실행 중 자가삭제"가 정적 분석을 막는 주된 장치다.

Step 1. 탐지 반응 확인

후킹 환경에서 앱을 실행하면 탐지 직후 경고를 띄우고 종료한다. 이 경고 발생 시점이 탐지 루틴을 좁히는 단서가 된다.

# 후킹 부착 후 실행 시
[Warning] Illicit activity detected. Game will shutdown...
# → 루팅은 미탐지, 후킹/디버깅만 탐지. 탐지 주체 모듈을 찾아야 함.

Step 2. 자가삭제 모듈 식별 (/proc/[pid]/maps)

프로세스 메모리 맵에서 (deleted) 표식이 붙은 매핑을 찾는다. 실행 후 삭제된 모듈을 의미한다.

$ cat /proc/<pid>/maps | grep <pkg>
...
6f96…000 r-xp ... /data/data/com.example.game/<보안모듈>.sec (deleted)
6f96…000 r--p ... /data/data/com.example.game/<보안모듈>.sec (deleted)
6f96…000 rw-p ... /data/data/com.example.game/<보안모듈>.sec (deleted)

→ <보안모듈>.sec가 로드 직후 자가삭제되는 탐지 모듈로 추정된다.

Step 3. unlink 후킹으로 삭제 차단 (Frida)

unlink()를 후킹해 삭제 호출을 가로채면, 모듈 파일이 지워지기 전에 보존·복사할 수 있다. 아래는 타깃 비종속 범용 후킹이다.

const hook_unlink = Module.findExportByName(null, "unlink");
const unlink = new NativeFunction(hook_unlink, 'void', ['pointer']);
Interceptor.replace(unlink, new NativeCallback(function (pathname) {
  console.warn('[*] unlink path: ' + pathname.readCString());
  // 원래 unlink를 호출하지 않음 → 삭제 차단
}, 'void', ['pointer']));
# 결과
[*] unlink path: /data/data/com.example.game/<보안모듈>.sec
# 삭제가 차단되어 모듈 파일을 복사·보존 → 정적 분석 가능

Step 4. 복구 모듈 정적 분석 (Ghidra)

복구한 모듈을 디스어셈블러에 로딩하고 종료 메시지 문자열을 앵커로 탐지 루틴을 역추적한다.

  • 문자열 검색 "detected" → 종료 메시지 참조 지점 식별 (오프셋 생략)
  • 해당 문자열을 참조하는 함수 = <종료 루틴> — 후킹/디버깅/루팅 탐지 결과에 따라 앱을 종료
  • 이 루틴을 후킹으로 조작하면 보안 솔루션이 무력화되는 단일 지점이 된다 (구체 우회 코드·주소 비공개)
