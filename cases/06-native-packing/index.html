네이티브 코드 패킹 — 자작 데모 언패킹·덤프

직접 만든 데모(MBGuard-Demo-L3)의 네이티브 모듈을 암호화해 로드 순간에만 복호되게 하고 — 그 순간을 덤프해 원본을 복원하고(공격), 로더를 하드닝해 다시 막는(방어) 공방을 실측으로 보인다 · 완전공개 · 재현 가능
완전공개 · 자작 데모. 본 사례의 앱·네이티브 모듈·빌드·덤프 스크립트는 전부 직접 작성했다. 상용 제품이 아니며, 암호 키는 일부러 바이너리에 내장해 "패킹이 보안 경계가 아님"을 보이는 교육 목적이다. 공격 대상이 자작물이라 마스킹이 필요 없다.
왜 패킹인가. 안티치트·RASP 분석의 첫 관문은 코드를 읽는 것이다. 그래서 상용 보호는 네이티브 로직을 암호화해 디스크 바이너리에서 읽히지 않게 하고, 실행 직전에만 메모리에서 복호한다(패킹/언패킹). 이 데모는 그 구조를 최소 재현하고, 실제 분석에서 쓰는 "복호 순간 덤프"로 복원해 보인다. 상용 사례(암호화 JNI 런타임 복원)의 안전한 자작 버전이다. → 관련: 상용 앱 암호화 JNI 복원

난이도 단계 — 무엇을 암호화하는가

레벨보호정적 분석에서 보이는 것
L1무방비문자열·로직 전부 평문 — strings·디스어셈블로 즉시 읽힘.
L2문자열 XOR 암호화 + 심볼 스트립탐지 문자열·내부 함수명은 가려지나, 로직(명령어)은 디스어셈블로 그대로 보임.
L3로직 자체 암호화(패킹)디스크 바이너리엔 암호문만. 로직은 로드 순간 메모리에서만 복호 → 정적 분석 불가, 런타임 덤프 필요.

L3 설계 — 2차 ELF 인메모리 로드

로더 .so평문·유일 탑재
→
암호화 에셋libmbguard_lv2.so.enc (ChaCha20)
→
복호메모리 버퍼 = 평문 ELF
→
memfd_create디스크 미기록
→
android_dlopen_extfd에서 로드
→
내부 모듈 실행탐지 워처 가동

진짜 탐지 로직(루팅/Frida 12종)은 별도 모듈 libmbguard_lv2.so로 빌드한 뒤 ChaCha20으로 암호화해 에셋으로만 넣는다. APK의 네이티브 lib에는 얇은 로더만 들어간다. 로더는 실행 시 에셋을 복호해 디스크를 거치지 않고(memfd) 메모리에서 바로 로드한다. JNI 심볼은 로더가 소유하고, 내부 모듈의 C 함수로 위임한다(수동 로드 모듈의 JNI 미등록 문제 회피).

① 정적 관점 — 디스크엔 암호문만

빌드된 APK를 열면 네이티브 lib에는 로더만 있고, 내부 모듈은 암호화 에셋으로만 존재한다(평문 ELF 아님).

# APK 내부(unzip -l) — lib/ 와 assets/
lib/arm64-v8a/libmbguard_loader.so    12760   ← 평문 로더(유일 탑재)
assets/libmbguard_lv2.so.enc         46040   ← 암호화된 내부 로직
# 내부 모듈 평문(libmbguard_lv2.so)은 APK에 없음(packaging 제외)

# 암호화 에셋 첫 4바이트
1a 8a e9 c8     ← ELF 매직(7f 45 4c 46) 아님 = 디스어셈블 불가

② 런타임 — 로드 순간 메모리에서 복호

앱 실행 시 로더가 에셋을 복호해 메모리에서 내부 모듈을 올린다. 실기기(arm64, 루팅) logcat.

# 앱 실행 직후 logcat (MBGuard 태그)
I MBGuard: inner module decrypted in memory (46040 bytes), ELF magic OK
I MBGuard: MBGuard-L3 inner module started (unpacked in memory)
I MBGuard: L3 loader ready — inner watcher running (unpacked)
W MBGuard: DETECT [8] su      ← 복원된 내부 로직이 실제로 구동(루팅 탐지)
W MBGuard: DETECT [9] magisk
W MBGuard: DETECT [11] mount

memfd_create + android_dlopen_ext(library_fd)로 디스크를 거치지 않고 로드했다(실기기에서 성공, 파일 fallback 불필요).

③ 공격(1라운드) — 복호 순간 덤프로 복원

아래는 자기방어가 없는 로더 기준이다(다음 ④에서 하드닝한다).

정적으로 안 읽히면, 복호가 끝나 평문이 메모리에 존재하는 바로 그 순간을 잡는다. 로더가 평문 ELF를 memfd에 기록하는 write() 호출을 Frida로 후킹해 통째로 덤프한다.

// dump_lv2.js — write(fd, buf, len)에서 ELF 매직이면 buf 전체 덤프
Interceptor.attach(Module.getGlobalExportByName("write"), {
  onEnter(args) {
    const len = args[2].toInt32();
    const b = new Uint8Array(args[1].readByteArray(4));
    if (b[0]===0x7f && b[1]===0x45 && b[2]===0x4c && b[3]===0x46)  // \x7fELF
      new File(OUT,"wb").write(args[1].readByteArray(len));        // 평문 ELF 저장
  }
});
# 실행 결과 (florida -H 로 spawn)
[dump] 평문 ELF 포착(write→memfd): 46040 bytes
[dump] 저장: /data/.../files/dumped_libmbguard_lv2.so

# 덤프 == 원본 모듈 검증
덤프 .so   SHA256 : b99a67ee…50151899
원본 inner SHA256 : b99a67ee…50151899
바이트 일치: True   + mbg_start/mbg_statuses/mbg_coins 심볼 존재 = Ghidra 분석 가능

확정 덤프한 .so가 원본 내부 모듈과 SHA-256 바이트 단위로 완전 일치 — 암호화된 모듈을 로드 순간에 떠서 분석 가능한 원본 그대로 복원했다.

④ 방어(2라운드) — 로더 하드닝으로 덤프 차단

로더가 평문 스텁이면 위처럼 쉽게 뚫린다(Ghidra에서 키·에셋명·언패킹 흐름이 그대로 보임). 그래서 로더 자체에 자기방어를 넣었다 — 상용 패커가 하는 세 가지.

방어내용효과(Ghidra/런타임)
심볼 스트립 + visibility hidden-s -fvisibility=hidden.dynsym에 JNI 3개만 노출, 내부·anti-debug 함수 전부 은닉
문자열 난독화 + 로그 제거키·논스·에셋명·TracerPid:·dlsym 이름·/proc 경로 XOR 난독, 로그 메시지 전면 삭제동작을 알려주는 평문 문자열 0건(남는 건 필수 JNI 심볼뿐)
init_array anti-debug로드 시점 생성자에서 TracerPid·maps·스레드명(comm) 스캔 → 감지 시 복호 키 오염디버거/Frida 존재 시 복호가 비-ELF로 실패(anti-dump)
 
# 하드닝 로더 정적 검사
llvm-strings libmbguard_loader.so | grep -E 'key|TracerPid|frida|mbg_|/proc'  → 0건
llvm-nm -D libmbguard_loader.so
  Java_..._nativeInit / getStatuses / getCoins          ← 노출 심볼 = JNI 3개뿐

# 동일한 Frida 덤프를 하드닝 로더에 재시도
[dump] write() 후킹 설치 — 대기 중…
(내부 모듈 구동 로그 없음)       ← init_array가 Frida 포착 → 키 오염 → 복호 비-ELF
덤프 파일: ABSENT            ← 평문 ELF가 메모리에 생성되지 않음 → 덤프 불가

★핵심: florida는 파일 경로 없는 익명 주입이라 maps의 "frida" 경로·TracerPid(스폰 후 0) 검사를 회피한다. 1차 방어(경로·TracerPid)는 실패했고, 스레드명(gum-js 등) 스캔을 추가하자 비로소 포착됐다 — 방어도 실측으로 검증해야 함을 보여준다.

교훈 — 공방은 라운드로 이어진다. 패킹만으론 복호 순간 덤프에 뚫린다(1라운드). 로더에 스트립·난독화·init_array anti-debug를 더하면 naive 덤프는 막힌다(2라운드). 그러나 이것도 결정적 경계가 아니다 — init_array 방어선을 먼저 무력화(스레드명 스푸핑·thread-hide·스캔 후킹)하면 덤프는 다시 가능하다. 키가 클라이언트 안에 있는 한 평문은 어느 순간 메모리에 존재하기 때문이다. 난독화·패킹·anti-debug는 공격 비용을 라운드마다 올리는 지연 수단일 뿐, 신뢰 기점은 클라이언트 밖 — 서버 검증 또는 하드웨어 기반 증명에 둬야 한다.

방어 측 권고

  • 패킹은 분석 지연용으로만 쓰고, 무결성·인가 판정을 서버로 이전한다(클라 판정은 복원·우회 가능).
  • 키를 클라이언트에 두지 않는다 — 원격 키 전달/증명(remote attestation), 하드웨어 보안요소(StrongBox/TEE) 결합.
  • 복호 시점 덤프를 올리려면 단계적 복호·anti-dump(복호 직후 재암호·memfd 탐지)를 병행하되, 어느 것도 결정적 경계가 아님을 전제로 설계한다.
