게임 엔진별 전투 분석 비교 — Unreal · Unity

동일한 분석 파이프라인으로 엔진별 대표 사례를 분석하고, 보안 설계의 잘된 점·안된 점과 개선방안을 비교한다 · 개인 보안 연구 · 방어 목적 · 대상 익명화
방법론 기둥 — 보안 솔루션 우회 → SDK 덤프 → 전투 로직 → Frida 실발동 검증 → 클라/서버 권위 판별. 각 게임을 같은 단계로 분석해, 무엇이 실제로 뚫렸고 무엇이 방어됐는지 실측 기반으로 비교한다. → 방법론 보기
공개 범위·대상 고지. 본 비교는 공개된 상용 게임을 대상으로 한 개인 보안 설계 연구로, 특정 퍼블리셔의 의뢰·인가를 받은 것이 아니며 대상은 익명화(엔진·장르 수준)했다. 결과는 방법론·설계 평가·개선방안 수준으로만 기술하며, 실제 오프셋·주소·동작 우회 코드·암호화 키·완성된 치트는 포함하지 않고 어떤 조작 도구도 배포하지 않는다. 판정은 확정(런타임 실측)과 미규명(실측 미확보)으로 구분 표기한다.

분석 파이프라인 (공통 6단계)

  1. 보안 솔루션 적용 시 우회 — 안티치트·RASP가 계측(Frida)을 막으면 먼저 그 탐지·종료 벡터를 규명·회피한다. 계측이 안 되면 그 뒤 단계가 전부 불가능하다.
  2. SDK 덤프 — 엔진 메타데이터에서 클래스·함수 구조를 추출한다. 커스텀 암호화 모듈이면 난도가 극단적으로 오른다(전용 복호기 자작 필요).
  3. 전투 로직 판별 및 분석 — HP·데미지·사망 판정이 어느 함수·값에 있는지 정적으로 좁힌다.
  4. Frida 후킹으로 실제 로직 판별 — 정적 후보를 런타임 후킹으로 실제 발동 검증한다(코드 존재 ≠ 런타임 사용).
  5. 클라/서버 권위 유무 판별 — 그 값이 클라이언트에서 결정되는지, 서버가 검증·감사하는지 조작 A/B로 가린다.

아래 두 비교는 이 6단계를 실제 게임에 적용한 결과다. "서버가 검증한다 / 이 값은 화면 표시용 복제본(미러)이다" 같은 긍정 결론도 실측 전에는 미규명으로 남긴다.

Unreal Engine — 사례 A(UE4) vs 사례 B(UE5)

둘 다 Unreal 기반에 네이티브 안티치트를 얹었지만, 전투 핵심값의 신뢰 위치에서 정반대 결과가 나왔다.

단계 사례 AUE4 · 오픈월드 액션 RPG 사례 BUE5 · 모바일 액션
1. 우회 florida spawn 시 검은 화면·ANR(앱 응답 없음)로 실패 → 특정 주입 방식이 필요. 루트 탐지는 스레드/파일 denylist 회피로 통과. florida spawn은 생존(탐지 미발동), late-attach는 t+7s에 네이티브 자가종료. .text 후킹 시 ~35s "보안 검증 실패"류 팝업 후 종료(보안솔루션 .text 무결성 서명 탐지). 트램폴린 없는 리다이렉트·단발 하드웨어 워치포인트만 탐지 회피 가능.
2. SDK 덤프 엔진 바이너리가 심볼 노출(unstripped) — 분석 지점 식별은 쉬우나, 런타임 핫패치(코드 재작성)로 정적 오프셋이 수시로 무효화되어 재도출이 강제된다. 엔진 바이너리 완전 stripped(심볼 0) → UE 오브젝트 리플렉션으로 4만+ 클래스를 런타임 순회해 구조를 복원. SDK 필드 오프셋은 가려짐.
3. 전투 로직 전투 로직이 Mono C#(스크립트) 레이어에 존재함을 식별. 스킬 히트 → 데미지 적용 경로를 식별. 데미지 값은 암호화 정수(XOR 기반)로 저장되어 평문 값-스캔이 불가능.
4. Frida 실로직 노출된 심볼을 직접 후킹해 전투 핸들러의 실제 발동을 확인. .text를 건드리지 않는 함수 포인터 리다이렉트 + 단발 하드웨어 워치포인트로 보안솔루션 무결성 검사를 피해 적용 데미지 값 read에 성공.
5. 권위 확정 클라이언트 저장 HP가 전 계층 미러임을 규명 — 값을 동기화 핀/조작해도 캐릭터는 정상 사망(로컬 조작 무효).
확정 반면 크리티컬 강제 발동(항상 크리) 조작은 실제 반영 — 크리 판정은 클라이언트 영향권(HP 미러와 달리 조작이 통함).
미규명 서버 권위 자체·데미지 수치 경로 조작 가능성.		 확정 아군 HP 무적(값 고정 시 피격 무피해·생존) + 몬스터 HP 조작(값 감소 → 즉시 처치 등) + 이동속도 조작(스피드핵) 실제 작동 — HP·이동 등 핵심 전투값이 클라이언트 권위.
미규명 데미지 수치 조작(진짜 공격력 필드 미발견 + 암호화 정수).
6. 결론 전투 핵심값(HP) 보호가 우수 — 접근 가능한 값은 전부 미러. 분석 방해(핫패치)도 효과적. 안티치트 무결성(.text)·데미지 암호화는 견고하나, HP·이동이 클라 신뢰라 아군 무적·몬스터 HP 조작·스피드핵이 성립.

잘된 점

  • 사례 A — 접근 가능한 HP가 전부 미러(로컬 조작 무효). 런타임 핫패치로 정적 분석 비용을 크게 올림.
  • 사례 B — .text 무결성 서명으로 트램폴린(코드 패치) 후킹을 차단. 데미지를 암호화 정수로 저장.

안된 점

  • 사례 A — 엔진 심볼이 노출(unstripped)되어 전투 후킹 지점 식별이 쉬움. 크리티컬 강제 발동 조작이 작동(크리 판정이 클라 신뢰).
  • 사례 B — HP·이동속도가 클라 권위 → 아군 HP 무적 + 몬스터 HP 조작(즉시 처치 등)·스피드핵이 실제로 성립(치명). 오브젝트 테이블은 .text-free 후킹에 노출.
개선방안. 사례 B — 아군/몬스터 HP·이동속도 등 핵심 전투값을 서버 권위/검증으로 이전하고, 비정상 델타(순간 이동·무피해·몬스터 HP 급감)를 서버가 거부·롤백. 데미지 암호화 정수는 복호 측 무결성 검증이 약하므로 서버 재계산·교차검증을 병행. 사례 A — 전투 관련 심볼을 strip·은닉해 후킹 지점 노출을 줄이면, 이미 우수한 미러 설계와 맞물려 분석 비용이 더 커진다.

Unity (IL2CPP) — 사례 C vs 사례 D

둘 다 Unity IL2CPP지만, 코드 보호 강도와 전투값을 지키는 방식이 대조적이다.

단계 사례 CUnity IL2CPP · 오픈월드 RPG 사례 DUnity IL2CPP · 액션 RPG
1. 우회 상호 ptrace 등으로 attach를 전면 차단 → 함수 포인터 리다이렉트(.text 무접촉)로 안티치트 탐지 없이 foothold 확보. 상용 안티치트 + 네이티브 보안솔루션 환경. IL2CPP 코드 영역은 트램폴린 스캔 대상이 아니라 후킹이 생존 → 브리지 기반 계측으로 접근.
2. SDK 덤프 메타데이터 암호화 + 커스텀 런타임 → 전용 복호기를 자작해야 8만+ 클래스 순회가 가능. 분석 진입 난도 최상. 표준 IL2CPP(메타데이터 평문)라 덤프가 상대적으로 용이. 데미지 공식을 전 파이프라인 역산(복원 완료).
3. 전투 로직 스탯(FightProp) 시스템 식별. 라이브 HP%·데미지 값 read 성공. 데미지는 클라이언트 계산. 히트 디스패처와 곱연산 공식을 식별.
4. Frida 실로직 함수 포인터 리다이렉트로 전투 메서드를 후킹하고, 데미지 계산 함수를 화이트박스로 역산. 브리지 데미지 로거로 실데미지 궤적 캡처 + 서버 전송 패킷(protobuf) 관찰.
5. 권위 확정 데미지는 클라 계산이지만, 표시 데미지·HP는 화면 표시용 — 덮어써도 게임플레이 무영향. 실제 HP는 값마다 다른 salt로 인코딩되어 값-스캔이 봉쇄. 6개 각도의 조작이 전부 무효(실적용 격리) 실증. 랭킹/경쟁 콘텐츠: 분석 과정에서 보안솔루션 메모리 무결성 · 서버 챌린지-응답 · 전투 로그 감사 구조를 확인 — 조작 시 서버 검증·밴 대상.
미규명 실제 밴 발동은 라이브 계정 리스크로 조작 미실행(구조 분석 기반 평가).
확정 비랭킹(일반) 콘텐츠: 동일 조작이 그대로 반영되고 밴 없음 → 일반 전투는 클라이언트 신뢰(서버 감사 미적용).
6. 결론 코드 보호(복호기 자작 강제)와 표시/권위 분리 + salted 인코딩이 모범적. 단일 클라 핸들로는 전투값 조작 불가. 서버 감사·보안솔루션 검증 구조는 랭킹 콘텐츠에 국한(분석에서 확인). 비랭킹 전투는 클라 조작이 반영되고 데미지 공식·패킷 구조도 노출됨.

잘된 점

  • 사례 C — 커스텀 메타데이터 암호화로 분석 진입장벽 최상. 표시값과 실제 적용값을 분리하고 실제 HP를 salt 인코딩해, 조작을 구조적으로 무의미화.
  • 사례 D — 랭킹 콘텐츠는 서버 감사·검증 구조를 갖춤(분석 확인 — 랭킹 조작은 서버 검증·밴 대상). 보안솔루션 보안 값·검증 패킷으로 메모리 무결성 보강.

안된 점

  • 사례 C — (실측 범위 내) 치명적 클라 취약은 미발견. 분석 비용이 매우 높아 실제 적용값까지의 도달 난도가 높다 — 방어 측엔 강점.
  • 사례 D — 비랭킹 전투는 클라 조작이 그대로 반영(밴 없음). 데미지 공식이 클라에서 완전 복원되고 전송 패킷 구조가 노출 → 방어가 랭킹 서버 감사에만 의존.
개선방안. 사례 D — 서버 감사·검증을 랭킹뿐 아니라 일반 전투 전반으로 확대하고, 데미지 계산을 서버로 이전하거나 핵심 상수를 서버에 보관하고, 전송 패킷을 암호화·서명해 공식 역산·예측 비용을 올린다(현재는 랭킹 밖 전투가 클라 신뢰). 사례 C — 현재의 표시/권위 분리와 salted 인코딩 수준을 민감 전투값 전반에 유지하면 충분하다(모범 사례).

종합 — 네 사례가 주는 교훈

축비교
코드 보호(분석 난도)사례 C(커스텀 메타데이터 암호화) > 사례 A(런타임 핫패치) > 사례 B · 사례 D(표준 덤프 가능).
전투값 방어사례 C(표시/권위 분리+salted, 조작 무효 실증)가 최상 · 사례 D(랭킹=서버 감사·검증 구조 확인, 단 비랭킹은 클라 조작 반영) · 사례 A(HP 미러 실증, 단 크리티컬 강제는 작동). 사례 B가 상대적으로 취약(아군·몬스터 HP·스피드핵 실증).
안티치트의 한계.text 무결성·주입 차단만으로는 전투 값 조작을 막지 못한다 — 핵심 값은 서버 권위/검증 또는 암호화 격리가 필요(사례 B가 반례, 사례 C가 모범, 사례 D는 랭킹 한정 모범).
방법론 규율"서버 권위 / 미러 / 화면 표시용" 같은 긍정 결론도 실측 전엔 미규명으로 남긴다. 사례 A·사례 B의 데미지 권위는 미규명으로 표기했다.

핵심 메시지 — 우회 자체가 목적이 아니라, 어떤 값이 실제로 조작 가능한지를 실측으로 가려내 방어 개선의 근거로 잇는 것이 분석의 목적이다.
